## 1. Feature Context

- [ ] `p2` - `cpt-frontx-dashboard-feature-dashboard-root-types`

### 1.1 Overview

This is a **type-catalog feature**, not an actor-flow feature. It declares the trimmed Dashboard root, which embeds its layout, and the Theme type. The FEATURE template's flow, process, and state sections are reduced to stubs; the catalog lives in section 6, Type Catalog.

### 1.2 Purpose

Concrete catalog of the dashboard root types of DESIGN section 3.1 (Dashboard root, trimmed, and Theme). Delta against the prototype: `report` is removed and `dashboard` is trimmed to `id`, `name`, `description`, and the embedded `layout`; `theme` is unchanged apart from the sentence that referred to the removed report. Dashboard instances are GTS-typed and delivered by the backend as the dashboard definition (`cpt-frontx-dashboard-interface-dashboard-payload`; DESIGN section 3.1, Instance source). The backend stores and returns only that definition; the consuming product may author it or generate it, and in either case it validates against these types. The theme lives on the frontend: the template owns its Theme instance, and the backend does not supply it. For a generated dashboard, these types let the consuming project validate the root of the definition and its embedded layout before it is shown.

**Declaring package**: `dashboard-viewer`.

**Requirements**: `cpt-frontx-dashboard-fr-domain-model`, `cpt-frontx-dashboard-fr-theme`, `cpt-frontx-dashboard-fr-backend-source`, `cpt-frontx-dashboard-fr-generated-dashboards`

**Principles**: `cpt-frontx-dashboard-principle-gts-contracts`

### 1.3 Actors

N/A — type-catalog feature. The catalog is consumed by the runtime type system (Viewer host and widget MFEs), not by an end-user actor. No human actor flows are authored.

## 5. Definitions of Done

### Type Catalog Definition of Done

- [ ] `p1` - **ID**: `cpt-frontx-dashboard-dod-dashboard-root-types-catalog-complete`

The system **MUST** declare `gts.frontx.m.dashboard.dashboard.v1~` with only the four trimmed fields (`id`, `name`, `description`, `layout`) and `gts.frontx.m.dashboard.theme.v1~` in `dashboard-viewer`, and **MUST NOT** declare a report type.

- Every concrete is authored with a full JSON Schema declaration.
- Every identifier follows the GTS identifier grammar and the ID-form convention of DESIGN section 3.1 (types end with `~`, instances do not).
- Every `x-gts-instance-ref` operand is valid under GTS v0.17, and every `$ref` resolves to a declared type.
- The Dashboard `id` is a combined anonymous instance identifier (`gts.frontx.m.dashboard.dashboard.v1~<uuid>`, UUID generated by the backend); the Dashboard declares no separate `type` field.
- The layout is embedded in the Dashboard; no layout reference or separate layout instance exists.
- The dropped prototype fields (`visibility`, `short_link_token`, `publication_state`, `enabled_state`, `audience`) and the report type are not reintroduced.
- The Dashboard root declares no `theme` field; the Theme instance is template-owned frontend content and is not part of the dashboard definition.

**Constraints**: `cpt-frontx-dashboard-constraint-gts-id-convention`

## 6. Type Catalog

### 6.1 Dashboard

**GTS ID**: `gts.frontx.m.dashboard.dashboard.v1~`

**Description**: Trimmed top-level container of a dashboard: identifier, name, description, and the embedded layout. A Dashboard instance is the dashboard definition the backend stores and returns: the layout is embedded, and each layout cell embeds one widget instance (presentation configuration plus `params`); the definition carries no widget data and no theme. The consuming product may author or generate it. The demo package serves a static definition of the same shape. The prototype's visibility, short link, publication, enablement, and audience fields are dropped; a consumer may derive a subtype that adds them.

**Schema**:

```json
{
  "$id": "gts://gts.frontx.m.dashboard.dashboard.v1~",
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "Dashboard",
  "description": "Trimmed top-level container defining a named dashboard with its embedded layout.",
  "type": "object",
  "required": ["id", "name", "layout"],
  "properties": {
    "id": {
      "type": "string",
      "x-gts-instance-ref": "/$id",
      "description": "Combined anonymous instance identifier: the dashboard type chain followed by a UUID generated by the backend, for example gts.frontx.m.dashboard.dashboard.v1~<uuid>. No separate type field exists."
    },
    "name": {
      "type": "string",
      "description": "Human-readable dashboard name."
    },
    "description": {
      "type": "string",
      "description": "Optional longer description of the dashboard purpose."
    },
    "layout": {
      "$ref": "gts://gts.frontx.m.layout.layout.v1~",
      "description": "The dashboard's layout, embedded: the grid columns and the cells, each embedding one widget instance."
    }
  }
}
```

**Cross-references**:
- No abstract base (flat single-segment chain).
- Related types: `gts.frontx.m.layout.layout.v1~` (`feature-layout-types`), embedded through `$ref`.
- The prototype's `report` type is not ported; each widget requests its own data from the backend, so no report payload exists.
- Theme: the Dashboard does not reference a theme; the template applies its own frontend-owned Theme instance (section 6.2).
